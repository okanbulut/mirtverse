Item Response Theory with mirt and mirtverse

Chapter 14 Large language models as a colleague

Learning goals. After this chapter you can

  • describe what a large language model (LLM) does and why its output varies and can be wrong;
  • use an LLM through mirtverse to draft analysis code, write items and score responses, and see exactly what is sent to it;
  • explain why every LLM output in testing needs a check, and use mirtverse’s checks for wrong keys, weak distractors and machine-human agreement;
  • make LLM work reproducible by recording and replaying responses, and say what to report about an LLM in a technical manual or paper.

Key terms: large language model, prompt, hallucination, human-in-the-loop, automatic item generation, automated scoring.

14.1 The ideas

A large language model is a neural network trained on a very large amount of text to predict the next piece of text. Given instructions and context, the prompt, it continues them, and that one ability is enough to write items, explain results, score essays against a rubric or draft code. Claude, GPT and the open models that run on a laptop through Ollama all work this way.

For a psychometrician, three properties matter more than how the network works:

  • Its output is a sample. The same prompt can give different answers on different runs and with different versions of the model. An LLM is not a function with a fixed value; it behaves more like a rater.
  • It can be fluently wrong. A model can write an item with no correct option, invent a reference or misread a rubric, in the same confident style as a correct answer. Such errors are called hallucinations, and they are found only by checking.
  • What you send leaves your computer. Unless the model runs locally, the prompt goes to a provider. Test content and response data may be confidential, so what is sent has to be a decision, not an accident.

These properties lead to the way mirtverse uses LLMs, which is also a good rule for any testing program (Hao et al. 2024; Bulut et al. 2024): The model drafts, something else checks, and a person decides. Generated items are answered again by a second, independent model call that does not see the key. Machine scores must agree with human scores, overall and within groups, before they count, following the framework of Williamson, Xi and Breyer (2012). Anything the model is unsure about goes to a person.

mirtverse talks to models through the ellmer package. mv_ask_setup() chooses a provider once: Claude or OpenAI with your own API key, or Ollama for a free model that runs on your own computer. This chapter instead runs in replay mode: mv_llm_replay() answers every request from a file of recorded responses that comes with mirtverse, so the examples need no key, no internet connection and give the same results for every reader. Those responses were written by hand to show what a model returns, including a few deliberate mistakes; they were not produced by a live model.

14.2 Example 1: From a sentence to a tested script

mv_ask() turns a plain-language request into an analysis plan and the plan into an R script built from tested templates. The model never writes code and never sees the responses: It sees the request and a summary of the columns. You can see that payload before anything is sent with dry_run = TRUE:

# mirt's Science data: 392 respondents, 4 attitude items scored 1 to 4.
resp <- Science
request <- "Fit a graded response model to these attitude items, check the fit and explain the results."
mv_ask(request, data = resp, dry_run = TRUE)
#> This would be sent to recorded responses:
#> 
#> Request: Fit a graded response model to these attitude items, check the fit and explain the results.
#> 
#> Data: 392 rows, 4 columns.
#> Columns (name | type | distinct values | min | max | share missing | guessed role | categories):
#> - Comfort | integer | 4 | 1 | 4 | 0.00 | item | 
#> - Work | integer | 4 | 1 | 4 | 0.00 | item | 
#> - Future | integer | 4 | 1 | 4 | 0.00 | item | 
#> - Benefit | integer | 4 | 1 | 4 | 0.00 | item |

The payload holds the request, the number of rows and, for each column, its type, range, share missing and the role mirtverse guesses for it. With anonymize = TRUE the column names are replaced by codes as well. Now the real call, answered from the recording:

s <- mv_ask(request, data = Science, ask = FALSE)
s$parser
#> [1] "recorded responses"
s$plan$model
#> [1] "graded"
s$plan$assumptions
#> [1] "All four columns (Comfort, Work, Future, Benefit) are items scored 1 to 4."
#> [2] "No grouping column was mentioned, so no DIF analysis is included."         
#> [3] "Used the 4 columns that look like item responses as items."

The model chose the graded response model, kept the default steps, and stated two assumptions it made. Read them: An assumption is where a model fills a gap in your request, and a wrong one gives a wrong analysis that runs without error. The script itself is printed with s, and run with run_script(s).

14.3 Example 2: Writing items, and catching the mistakes

The assessment pipeline writes items for the cells of a blueprint. Each multiple-choice item comes with a key and a rationale for every option, and is then checked by a second call that answers it blind.

# A two-cell blueprint for a short Grade 7 numeracy quiz.
cells <- data.frame(content = c("Ratios and rates", "Measurement"),
                    cognitive = c("Apply", "Apply"), n = c(2, 2))
p <- mv_pipeline("Grade 7 numeracy", verbose = FALSE)
p <- set_blueprint(p, cells, construct = "Grade 7 numeracy", use = "classroom diagnostic",
                   population = "Grade 7 students")
p <- suppressWarnings(generate_items(p, n = 2))
p$items[, c("id", "stem", "key", "verify_answer", "key_check")]
#> # A tibble: 4 × 5
#>   id    stem                                       key   verify_answer key_check
#>   <chr> <chr>                                      <chr> <chr>         <chr>    
#> 1 G001  A recipe uses 3 cups of flour for every 2… A     A             agree    
#> 2 G002  A cyclist rides 45 km in 3 hours at a ste… C     C             agree    
#> 3 G003  A garden is 12 m long and 7 m wide. How m… A     B             disagree 
#> 4 G004  A water bottle holds 2.5 litres. How many… B     B             agree

Two of the four items have problems. The writer keyed the garden item (G003) as 84 m, which is the garden’s area, but the question asks for the fence around it, the perimeter of 38 m. The checking call answered B and the item is flagged. In the millilitre item (G004), one distractor is a length, not a volume, so no test taker would choose it:

f <- flags(p, stage = "generation")
f[, c("check", "target", "level", "value")]
#> # A tibble: 4 × 4
#>   check      target                   level  value                              
#>   <chr>      <chr>                    <chr>  <chr>                              
#> 1 key_check  G003                     block  key A, verifier chose B; Fencing a…
#> 2 distractor G004                     review D (implausible)                    
#> 3 coverage   Ratios and rates / Apply review 2 items for a target of 2          
#> 4 coverage   Measurement / Apply      review 2 items for a target of 2
p$items$verify_note[3]
#> [1] "Fencing around the garden is the perimeter, 2 x (12 + 7) = 38 m (option B); 84 m is the area, so the key appears to be wrong."

A block flag stops the pipeline at the next stage until a person fixes the item or acknowledges the flag. The coverage flags are a reminder that items are lost in review and field testing, so a pool needs more items than the blueprint asks for. Notice what the checks do not do: They do not show that the items measure Grade 7 numeracy, that they are fair, or that their difficulty suits the test. Content review and a field test still do that.

14.4 Example 3: Is a recording reproducible?

Replay makes a session reproducible in a strong sense: The same calls on the same data give the same output, on any computer. It also makes the limits of a recording visible. Change the request by one word and the recording has no answer for it:

tryCatch(
  suppressWarnings(generate_items(set_blueprint(mv_pipeline(verbose = FALSE), c(Algebra = 2)),
                                  n = 1)),
  error = function(e) conditionMessage(e))
#> [1] "This request is not in the recording examples.json. A recording answers only the exact calls it was made from. Use a live model (mv_llm_replay(FALSE), then mv_ask_setup()), or record the call with mv_llm_record()."

For your own work, mv_llm_record("session.json") saves every request and response while you use a live model, and mv_llm_replay("session.json") plays them back. Keep the file with your analysis, as you would keep the data and the code. When you report work that used an LLM, say which model and version you used and when, give the prompts (mirtverse’s are in its source code and in the recording), say what was sent and what was not, and describe how the outputs were checked.

  2. mv_ask(), generate_items() (twice, one call per blueprint cell), verify_items() (once per item, called by generate_items()) and score_open() (once per batch of 10 responses, from the example in system.file("replay", "examples.R", package = "mirtverse")).

Further reading

Hao et al. (2024) describe what large language models change in testing, from item development to score reporting. Bulut et al. (2024) discuss the opportunities and the ethical questions, and Williamson, Xi and Breyer (2012) remain the reference for evaluating automated scores.
